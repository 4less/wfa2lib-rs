Where the lookup stands

  • Per pair: about 13 keys a mate on bacteroides (strided fast-hit round, 26.4 M keys for 1 M pairs) and 23.5 on protal-mini (47 M keys, 41% of them absent from the index). The number of lookups is already minimal.
  • The lookup is about 12.5% of cycles, with no dominant instruction left. Its stalls are DRAM latency on the key line and the values, which the prefetches already hide in part.
  • Index layout changes for small keys and batched lookups across pairs were measured and gave nothing (rows above). Further gains have to come from keys with many values or from work outside the lookup.

Single-end mode

Single-end runs a reduced pipeline: it stops at anchors, never aligns, and writes PAF. Before v8 it could not be started at all, so the "before" column is v7 with only the start-up fix applied.

Wall time barely moves because the one gzip file is decoded on a single thread, which now caps the run: 8 threads take 0.79 s, 16 threads 0.74 s. Paired-end decodes each mate file on its own thread. Accuracy of the single-end output was not scored, only checked unchanged.

  • The machine has 24 hardware threads, so the 16 workers don't compete with each other.
  • Most of the gap is serial start-up: index load 59 ms (bacteroides) and 148 ms (protal-mini), plus the fast-hit probe, about 13 ms, on the first 2048 pairs. Some more is lost at the end, when threads finish their last batches at different times.
  • Of protal-mini's 148 ms load, 123 ms is deserialising the 373,000 reference names. On a 0.65 s run the serial part is roughly 11% of wall time; on real-sized inputs it shrinks to noise.
