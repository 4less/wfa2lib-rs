Where flexalign spends its time, before and after

The original build is flexalign main@7ea91cf, aligning with the C WFA2-lib. The speed build is the speed branch (5042afa) merged with main@3644c36, so it aligns with wfa2lib-rs. Now is main@97b81cc (tag perf/v8-single-end), after the two index-lookup rounds, the branchless syncmer pass and the anchor-pairing rework. All runs use the same hashed index and the same reads.

The "now" profile was bucketed into the same stages by symbol name; boundaries shift a little where LTO inlines across stages. 1-thread seconds swing by ±15% on this laptop as its boost clock changes, so the "now" total is v6's measured 15.5 s scaled by user cycles (48.5 G → 44.2 G, −9%).

Since the speed build (17.7 → 14.1 s)

  • Anchor building and sorting: 4.1 → 2.8 s. Anchors and anchor pairs are written straight into their Vec slots; built on the stack and copied, their wide loads stalled on store forwarding. Seed groups of the two mates are merged in one pass, and the pair sort no longer allocates or swaps.
  • Index lookup + seed emission: 5.6 → 4.0 s. flexalign reads flexmap's hashed key table itself (8 entries a line in one AVX2 compare), the early per-mate key fetch now actually runs, and flank distances are computed 8 cells at a time.
  • Syncmer and k-mer extraction: 2.5 → 1.5 s. The second pass no longer branches on the strand or on whether a k-mer is selected; both branches mispredicted often.
  • Index lookup is the largest stage again (4.0 s, 29%), then anchor building (2.8 s) and extension (2.7 s).

What improved most

  • Anchor extension and verification: 5.3 → 2.6 s (2.0×). This is the biggest single saving. Fewer anchors reach it, 17.1 → 10.1 per read, because the anchor gate is now on. fix_anchor fell from 10.7% of cycles to 0.6%.
  • Syncmer and k-mer extraction: 4.7 → 2.5 s (1.8×). It now uses a sliding-window minimum, AVX2 s-mer passes and k-mers rolled in registers.
  • Anchor building and sorting: 6.0 → 4.1 s (1.5×). Glidesort is gone. Short lists now use insertion sort, and anchor pairs use a permutation sort.
  • Parallelism. This is why the wall-time gain (2.1×) beats the CPU gain (1.4×). Each gzip mate file now inflates on its own thread, so workers no longer wait on input. Busy cores rose from 9 to 14 of 16.
  • Timers and glue: 0.8 → 0.2 s. The per-record clock_gettime calls are gone.

The switch from C WFA2-lib to wfa2lib-rs is not visible here. Gapped alignment takes 0.5% of CPU in both builds (about 0.1 s). Most attempts end early at the ANI abort: 2.0 dropped attempts per read against 0.07 successful ones.

Where there is still room

  1. Reject off-target pairs before full seeding.largest potential 95.4% of pairs (950,941 of 996,424) produce no record, yet each one runs the whole pipeline: syncmers, lookups, seeds, anchors and an alignment attempt. A cheap presence test could stop most of them after a few lookups. For example, look up a sparse subset of syncmers and stop early when none hit. The fast-hit probe aims at the opposite case, placing pairs quickly, and it switched itself off here (it placed 66 of the first 2048 pairs). This matters most for marker-gene databases like protal, where most reads are off-target.
  2. Make fewer anchor candidates.~0.5–1 s Anchor building is down to 2.8 s (20%) after the in-place rework. Seeds that cannot pass the gate could still be pruned before pairing, instead of building pairs and then gating them; each anchor also carries its own heap-allocated seed list.
  3. Index lookups: done for now.tried Down from 5.6 to 4.0 s. Batching keys across pairs, a one-pair look-ahead and inline values in the key table were all measured and gave nothing; the remaining misses are on keys with many values.
  4. Cut allocator traffic.~0.5–1 s malloc/free cost 1.2 s (7%), up from 1.05 s. Trying mimalloc or reusing per-worker buffers is cheap.
  5. Watch the input threads as thread counts grow.matters above 16 threads gzip inflate is 1.4 s of CPU spread over two dedicated threads. That is not the limit at 16 threads, but it will cap wall time somewhere around 2–3× more workers. libdeflate, or uncompressed or BGZF input, would raise that cap.

Not worth pursuing: the aligner itself (0.5%).
